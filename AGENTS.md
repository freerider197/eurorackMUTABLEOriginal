# AGENTS.md

Instructions for AI coding agents (Claude Code, Codex, Cursor, Copilot, Gemini and others).
Humans: start with `tomline/README.md`. Keep this file under 150 lines: only what an agent can't work out from the code.

## What this is

A fork of Mutable Instruments' Eurorack firmware. The work here is **Tomline** (`tomline/`): alternative firmware for the
Streams hardware that turns it into a pitched bass tom (BT) / low tom (LT) voice. Trigger into EXCITE 1, V/oct into
EXCITE 2, sound from OUT 1. It reuses the stock Streams drivers, calibration code and audio bootloader.

The owner is not a developer. Explain results in plain words, and ask before anything risky.

## Commands

```bash
# FIRST, every session: start from the newest tomline-firmware (the clone may be on master, which lags behind)
git fetch origin tomline-firmware && git checkout -B "$(git branch --show-current)" origin/tomline-firmware

# once per clone: the shared libraries are git submodules
git submodule update --init --depth 1 stmlib stm_audio_bootloader

# test: runs the real voice.cc + parameters.cc on a computer, writes build/tomline_*.wav. Run before every commit
g++ -O2 -I. -o build/tomline_render tomline/test/render.cc tomline/voice.cc tomline/parameters.cc && ./build/tomline_render

# panel test: runs the real ui.cc (knobs, buttons, pick-up, calibration entry) with driver stand-ins. Run after any ui.cc change
g++ -O2 -Itomline/test/stub -I. -o build/tomline_panel tomline/test/panel.cc tomline/voice.cc tomline/parameters.cc && ./build/tomline_panel

# firmware + audio update file (needs arm-none-eabi-gcc and numpy) -> build/tomline/tomline.bin, tomline.wav
make -f tomline/makefile TOOLCHAIN_PATH=/usr/ wav

# worst-case stack (main loop + both interrupts) must fit the 4 KB in tomline/tomline.ld. Run after every firmware build
python3 tomline/tools/stack_usage.py build/tomline/tomline.elf

# check an update file decodes back to the .bin, packet by packet
python3 tomline/tools/check_wav.py build/tomline/tomline.wav build/tomline/tomline.bin

# check the browser model still matches the firmware, sample for sample (needs node)
g++ -O2 -I. -o build/tomline_words tomline/test/words.cc tomline/voice.cc tomline/parameters.cc && ./build/tomline_words
node tomline/test/compare_browser.js
```

- Report the render results (pitch error per volt, OUT 1 range and rest level) and whether the firmware built.
- No `arm-none-eabi-gcc`? Say the firmware build was not run; don't claim it builds.
- There is no CI, linter or formatter. Do not add one unless asked.

## Layout

| Path | What it is |
| --- | --- |
| `tomline/tomline.cc` | Init, main loop, audio interrupt (trigger detection, DAC and PWM writes) |
| `tomline/voice.cc/.h` | The voice, fixed point, 31,088 Hz |
| `tomline/parameters.cc/.h` | Knob values to voice parameters (control rate, float) |
| `tomline/ui.cc/.h` | Knobs, buttons, LEDs, calibration, saved settings |
| `tomline/pickup.h` | Knob pick-up: a value waits for its knob to turn, then glides to it in 40 ms |
| `tomline/cv_scaler_import.cc` | Builds the stock `streams/cv_scaler.cc` unchanged |
| `tomline/tables.h` | Sine and 2^x tables, generated by `tomline/tools/make_tables.py` (don't hand-edit) |
| `tomline/tools/` | `encoder.py` (bootloader WAV encoder), `check_wav.py`, `make_tables.py` |
| `tomline/test/render.cc` | Desktop render test with a model of the analog stage |
| `tomline/test/panel.cc`, `test/stub/` | Desktop test of `ui.cc` with driver stand-ins |
| `tomline/browser/` | Browser model: `tomline.html` (shared online version), `index.html` (standalone copy) |
| `tomline/test/words.cc`, `compare_browser.js` | Check the browser model against the firmware |
| `tomline/release/` | Released `.bin` / `.wav`, plus the stock `streams_1.01_original.wav` to go back |
| `streams/`, `stmlib/`, `stm_audio_bootloader/` | Stock code Tomline builds on |
| Other module folders | Upstream Mutable Instruments code; not part of this project |

## Safety: hardware and stock code

- **Untested on a real module.** Never say something works on the hardware unless the owner confirmed it. Say "builds" or
  "renders" instead.
- Don't edit `streams/`, `stmlib/`, `stm_audio_bootloader/` or other modules. Tomline reuses them unchanged; wrap or copy
  into `tomline/` instead.
- Keep the flash layout: bootloader 0x08000000 (16 KB), app 0x08004000 (112 KB), settings 0x0801F000, calibration
  0x0801FC00. Moving these can brick an update or wipe the owner's calibration.
- Keep the encoder settings (`-s 48000 -b 12000 -c 6000 -p 256`): the Streams bootloader expects them.
- Never delete or overwrite `tomline/release/streams_1.01_original.wav`; it is the way back to stock.
- Only add a new file to `tomline/release/` when the owner asks for a release. Use the next version number; never
  overwrite an old one.
- Don't add packages, downloads or network calls without asking.

## Scope and workflow

- One task = one GitHub issue = one branch = one small PR. If the work grows past the issue, stop and say so; propose a
  follow-up issue instead of doing it.
- Before coding, restate the goal and "done when" in 2–3 lines. For anything touching flash layout, calibration, saved
  settings or the bootloader, describe the plan and wait for an OK.
- Branch from the newest `tomline-firmware` (first command above, before any work) and open the PR against it. Branch names: `<agent>/<issue-number>-<short-topic>`,
  e.g. `claude/12-lt-decay-range`.
- Commits: one change each. Subject ≤ 72 chars, imperative, no semicolon lists ("Fix LT pitch drift at high V/oct").
  Add a body only for the why.
- Add or update a check in `tomline/test/render.cc` for every voice or parameter change.
- Don't push to `tomline-firmware` or `master`. Open a PR and let the owner merge. `.github/pull_request_template.md`
  has the sections below.

## PR description

Keep it short. Use exactly these sections:

```
## What changed      (3–5 bullets, what you hear / touch first)
## Why               (link the issue: "Closes #N")
## How I tested      (render results; firmware built? check_wav ok?)
## Risks / not done  (untested on hardware, flash layout, calibration, release files)
```

## Browser model first

- Tests and demos run in the browser model first (`tomline/browser/`, online at
  https://claude.ai/artifact/Ad2fPxFnc93cGY7k4Hzxwt), then on the module.
- Its `BEGIN FIRMWARE PORT` block must stay bit-exact with `voice.cc` and `parameters.cc`. After changing either,
  update the port, run `compare_browser.js` (must say IDENTICAL), run `tools/make_standalone.py`, and republish the
  online version.

## Notes

- After a change to controls, setup or flashing, update `tomline/README.md` (control map, Flashing, Tests "Last run").
- Cheat sheets for the owner are pictures, not tables: the panel with unused controls greyed out and the used knobs and buttons
  highlighted and labelled with what they do, one view per layer. Current one: https://claude.ai/artifact/U51rhAbef4VycZWjVJHTs3;
  update it after every control change.
- Hand over a new `.wav` with the flashing steps from `tomline/README.md` ("Flashing") every time, even if not asked.
  Never hand over a plain `tomline.wav`: copy it to `build/tomline/tomline-test-<topic>-<short commit>.wav` and send that,
  so the owner can tell test builds apart.
